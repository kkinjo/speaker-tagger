## 1. 方針

### AI は補助であり、判断は人が行う

このアプリが AI に任せるのは**整文（ステップ3）だけ**である。要約（ステップ4）と、
誤変換の修正（ステップ2）は人の担当とする。

理由は、**AI の出力が自然な日本語になるため、間違っていても人が気づけない**こと。
文字起こしの誤変換を AI に推測で直させると、読んで違和感のない誤った議事録ができる。
議事録は発言の記録なので、読みやすさよりも「間違っていたら気づけること」を優先する。

この方針から次の3点が導かれる。

| 方針 | 実装 |
|---|---|
| AI が既存の内容を上書きする操作には、必ず人の承認を挟む | ②の確認モーダル（`src/components/ConfirmModal.tsx`） |
| 人が手で直した行は AI の上書きから保護する | `Refinement.edited`（第4.4章） |
| AI を通していない行が一目で分かる | ②の3列目の濃淡とステータス表示（第4.5章） |

### データはユーザーごとに完全に分かれる

共同編集はしない。すべての読み取りは `loadOwned(projectId, userId)`
（`src/lib/projects.ts`）を通り、他人のプロジェクトには触れられない。
`tests/isolation.test.mjs` がこれを検証している。

## 2. 工程の分割と「整文」の定義

議事録作成を4段階に分ける。本アプリが担当するのはステップ3まで。

| ステップ | 作業 | 担当画面 |
|---|---|---|
| 1 | 発言の区切りと話者の割り当て | ①話者整理画面 |
| 2 | 誤字脱字・固有名詞の誤変換の修正 | ①話者整理画面 |
| 3 | **整文**：口語の簡素化、語尾の処理 | ②整文画面 |
| 4 | 論点別の要約 | アプリ対象外（Word 出力後に別途 LLM へ） |

### 「整文」の定義

発言の意味を変えずに、文書として読める形へ整える作業。

**行うこと**

- フィラー（「えーっと」「あのー」「なんか」）の除去
- 言い淀み・言い直しの統合
- 冗長な繰り返しの圧縮
- 語尾の処理（**文体プリセットによって変わる**。②の第3章）

**行わないこと**（ステップ4との境界）

- 複数の発言をまとめる
- 前後の文脈から論点を再構成する
- 発言に含まれない情報を補う
- 発言が途中で終わっている場合に続きを補う
- 聞き取れていない箇所・意味の通らない箇所を推測で補う
- **文字起こしの誤変換を推測で直す**（ステップ2で確定済みとして扱う）
- 固有名詞リストにある語の表記を変える

1発言 = 1出力を厳守する。入力行数と出力行数は常に一致する。

この一覧はそのまま system プロンプトに入っている（`buildSystemPrompt()`、
`src/lib/refine.ts`）。仕様を変えるときはプロンプトも合わせて直すこと。

## 4. データ構造

### 4.1 保存先

`src/lib/kv.ts` のごく小さな KV 抽象に JSON で保存する。

- 既定はファイルシステム（`.data/`、`DATA_DIR` で変更可）
- `KV_REST_API_URL` / `KV_REST_API_TOKEN`（Vercel KV）もしくは
  `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` があれば Upstash Redis の REST API

| キー | 内容 |
|---|---|
| `u_name_{username}` | ユーザー名 → ユーザー id の索引 |
| `u_{userId}` | `User`（`settings` を含む） |
| `u_{userId}_projects` | `ProjectSummary[]`（一覧用） |
| `p_{projectId}` | `Project` 本体 |
| `p_{projectId}_words` | `ProjectWords`（単語列。更新頻度が低く量が多いので別キー） |
| `app_secret` | `APP_SECRET` 未設定時に自動生成した署名鍵 |

**音声ファイルの実体はサーバーに送らない。** ブラウザの IndexedDB
（`src/editor/audioStore.ts`）に置き、`Project.audio` にはメタ情報だけを持つ。
テキスト（`rawText`・参加者・整文結果）はサーバー側の KV に保存される。
したがって整文のためにテキストを外部 API へ送ることは、既存の設計方針と矛盾しない。

### 4.2 `Project`（`src/lib/types.ts`）

```ts
export type Project = {
  id: string;
  userId: string;
  title: string;
  createdAt: number;
  updatedAt: number;
  /** 左ペインの生テキスト。表の唯一の元データ */
  rawText: string;
  participants: Participant[];
  /** 直近に選んだ話者 id（MRU 順、先頭が最新） */
  mru: string[];
  /** pyannote が話者交代を検知した位置（rawText の文字オフセット） */
  hints: number[];
  /** 音声のメタ情報。実体はブラウザの IndexedDB */
  audio: { name: string; size: number; type: string } | null;
  imported: boolean;
  /** 整文結果。キーは本文ハッシュ（第4.3章） */
  refinements: Refinements;
  /** この会議固有の固有名詞（第5章） */
  glossary: string[];
  /** 文体プリセット id。未設定は formal 扱い（②の第3章） */
  promptPresetId?: string;
};
```

`refinements` / `glossary` / `promptPresetId` は後から足したフィールドなので、
それ以前に保存された既存プロジェクトには存在しない。読み込み時に
`normalizeProject()` が `?? {}` / `?? []` で補う（`promptPresetId` は
undefined のまま使い、`getPreset()` が既定へ倒す）。
`tests/normalizeProject.test.mjs` が検証している。

**保存量の見込み** … 整文結果は300行 × 100文字程度で 30KB 前後。`ProjectWords`
のような別キー化はしていない。将来 1MB を超えるようなら `p_{id}_refine` へ分離する。

### 4.3 行の同定方法

**表は保存していない。** `parseDoc(rawText, participants)`（`src/editor/parse.ts`）が
毎回 `rawText` を解析して `Block[]` を作る。`Block.index` は配列内の位置であり、
①で1行挿入・削除すると以降の全行がずれるため、永続的な ID として使えない。

そこで整文結果は **本文のハッシュ** をキーにする。

```ts
// src/editor/refine.ts
export function sourceKey(body: string): string;      // 16桁の16進文字列
export function blockSourceKey(block: Pick<Block, "body">): string;
```

- `speakers` は整文対象外なのでキーに含めない
- ①で行を挿入・削除・並べ替えても、本文が変わっていない行の整文結果は保持される
- 本文を1文字でも直した行は自動的に別キーになり、「原文のまま出力」へ戻る。
  「要再変換」という状態を別に持つ必要がない
- 同一本文の行（「はい」等）はキーが衝突するが、同じ入力に対する整文結果は
  同じでよいので実害がない

**実装はハッシュ関数に SHA-256 を使っていない。** 種を変えた FNV-1a 32bit を
2回かけ合わせた軽量な同期ハッシュである。整文画面は数千ブロックを毎レンダリング
走査しうるのに対し、Node の `sha256` はサーバー専用、ブラウザの Web Crypto は
非同期呼び出ししか無く、描画ループに混ぜられないため。衝突耐性は要求していない。
シグネチャ `(body: string) => string` は変えずに中身だけ差し替えられる。
`tests/sourceKey.test.mjs` が「本文が同じなら同じキー、違えば違うキー」を検証している。

### 4.4 `Refinement`

```ts
export type Refinement = {
  /** 整文後のテキスト */
  text: string;
  /** AI 出力後に人が手で直したか */
  edited: boolean;
  updatedAt: number;
};

/** キーは sourceKey(block.body) */
export type Refinements = Record<string, Refinement>;
```

`edited: true` の行は AI の上書きから保護される（第1章）。「原文のまま確定」した
行も `edited: true`・`text` は原文と同一になる（②の第7章）。

### 4.5 行ステータス（保存しない。描画時に導出する）

`RefineApp.statusOf()` が `refinements` と、クライアント側だけの一時状態
`transient` から毎回求める。

| ステータス | 導出条件 | 画面のラベル |
|---|---|---|
| 未変換 | `refinements[key]` が無い | **原文のまま出力** |
| 変換中 | 一時状態 `pending` | 変換中 |
| 変換済 | あり、`edited === false` | AI変換済み |
| 手動修正済 | あり、`edited === true` | 手修正済み |
| 失敗 | 一時状態 `error` | 失敗 |

**「未変換」というラベルを使わない理由**

整文結果が無い行は、出力画面でそのまま原文が採用される（③の第2章）。処理されて
いないのではなく、原文を採用している状態である。「未変換」と書くと、利用者は
「左と右のどちらが最終成果物なのか」が分からなくなる。

「変換中」「失敗」は保存しない。ブラウザを再読み込みすると消え、失敗した行は
「原文のまま出力」に戻る（整文結果が既にある行は、その結果が残る）。

### 4.6 API

| メソッド・パス | 内容 |
|---|---|
| `GET /api/projects` | 一覧（`ProjectSummary[]`） |
| `POST /api/projects` | 新規作成 |
| `GET /api/projects/{id}` | 1件取得（`{ project, settings }`） |
| `PATCH /api/projects/{id}` | 部分更新 |
| `DELETE /api/projects/{id}` | 削除（`p_{id}_words` も消す） |
| `GET /api/projects/{id}/words` | 単語列の取得 |
| `PUT /api/projects/{id}/words` | JSON 取り込みの保存（`words` / `rawText` / `hints` / `title` / `imported`） |
| `PATCH /api/settings` | `UserSettings` の部分更新 |
| `POST /api/refine` | 1発言の整文（②の第8章） |
| `POST /api/auth/signup` `/login` `/logout` | 認証 |

`PATCH /api/projects/{id}` が受け付けるフィールドは
`title` / `rawText` / `participants` / `mru` / `audio` / `refinements` / `glossary` /
`promptPresetId`。`glossary` は要素の `trim()` と空文字の除去を、`promptPresetId` は
`isPresetId()` による既知 id の検査をサーバー側でも行う。

`hints` と `imported` は PATCH では更新しない。JSON 取り込み時に
`PUT /api/projects/{id}/words` がまとめて保存する。

### 4.7 認証

`src/lib/auth.ts`。ユーザー名＋パスワード。

- パスワードは scrypt（ソルト付き、64バイト）でハッシュ化。照合は `timingSafeEqual`
- セッションは cookie `st_session`（HMAC-SHA256 署名、有効期限30日）
- 署名鍵は `APP_SECRET`。未設定なら生成して KV の `app_secret` に保存する
  （**本番では必ず設定する**）

## 5. 固有名詞

### 5.1 二層構成

| 層 | 内容 | 保持場所 | 編集 |
|---|---|---|---|
| 全体リスト | どの会議にも出る語 | `src/lib/glossary.ts` の `GLOBAL_GLOSSARY` | 開発者のみ |
| 会議固有リスト | その会議にだけ出る語（議案名、来賓の所属等） | `Project.glossary` | 利用者（②の第4章） |

使うときは `mergeGlossary(project.glossary)` が両方を結合し、`trim()` と
空文字の除去をしたうえで重複を取り除く。

### 5.2 全体リストを定数に置く理由

- 変更頻度が低く、変えるのは開発者だけなので編集 UI が要らない
- Git で差分が追えるため、いつ何を足したかが残る
- 認証まわりに管理者権限の概念を足さずに済む

変更にはデプロイが必要になる。避けたい場合は環境変数（改行区切り）へ置き換えられるが、
現状は定数で足りている。

### 5.3 全体リストの中身（`d7e22b3` 時点で29語）

| 分類 | 語 |
|---|---|
| 連合会・組織 | 九附後連 / 九附連 / 九附P連 / 九州地区国立大学附属学校PTA連合会 / 全附P連 / 全附 / 教育後援会 / 後援会 / PTA / P / 連合会 / 事務局 |
| 学校・地区名 | 附属 / 附属小 / 附属中 / 小倉 / 久留米 / 福教大 / 特支 |
| 会議・役職まわり | 会長会 / 主管校 / 単位校 / 単位会 / 学校園 / 校園 / 議決権 / 委任状 |
| 会議名 | 宮崎大会 / 琉球大会 |

**人名と所属はここに入れない。** 参加者リストとして別途プロンプトへ渡すため
（②の第8.4章）。会議固有の語は `Project.glossary` 側。

### 5.4 このリストの用途

登録したリストは3か所で使える。**実装済みは1のみ。**

1. **整文（実装済み）** … AI に「これらの語は表記を変更しないこと」として渡す
2. ①の一括置換（**未実装**）… 誤変換を機械的に直す。「誤変換例 → 正しい表記」の
   対応表が必要になるため、今の `string[]` では実現できない
3. WhisperX の `initial_prompt`（**未実装**）… Colab 側に貼り付けて語彙を寄せる

型を `string[]` で始めたのは、1 だけなら語の一覧で足りるため。2 を実装する段階で
`{ term: string; variants: string[] }` へ広げる。最初から対応表の形にすると、
入力が倍になって利用者の負担が増える。

## 6. 未決事項

### 6.1 `GLOBAL_GLOSSARY` の育て方

実際の議事録から拾った語を随時追記する運用。追記の基準（どこまで略称を入れるか）は
決めていない。

### 6.2 プロジェクト一覧への整文進捗の表示

`○/○ 行` を一覧に出すかどうか。`ProjectSummary` への追加が必要になるため、
必要と分かってから。現状 `ProjectSummary` は `id` / `title` / `createdAt` /
`updatedAt` / `hasAudio` のみ。

### 6.3 文体（体言止め）の到達点

`formal` プリセットを「可能な範囲で体言止め」から「残すほうに理由を要求する」書き方へ
変更した後も、実際の出力は**常体化にとどまり体言止めには至っていない**
（「展開しています」→「展開している」）。文中の「〜なんですけど」は敬体のまま残るため、
敬体と常体が混在する。

実用上の支障は無いため当面このままとする。さらに強めるか、常体への統一を明示するかは未決。

### 6.4 プロンプトキャッシュが効いているか

`src/lib/refine.ts` は system に `cache_control: { type: "ephemeral" }` を付けているが、
system が1,000トークン前後で最小キャッシュ長に届かない可能性がある。届かない場合も
エラーにはならず素通りするため実害はない。実運用で `usage.cache_read_input_tokens` を
見て判断する（**現状コードは `usage` を読んでおらず、判断材料が取れていない**）。
